# Phase 11 — Observability & Error Handling

**Goal:** Every request is traceable, every error is consistent, every metric is available. After this phase you can debug a production problem from logs alone.

**Problem doc sections:** §21, §22, §23

---

## Requirements

### Request tracing
- Every request gets `request_id = req_<uuid>` (generated by middleware if missing)
- `request_id` appears in:
  - Response header `X-Request-Id`
  - Every log line during that request
  - Any downstream HTTP call (forwarded as `X-Request-Id`)
  - Any published event (in `data.request_id`)
  - DB rows: `outbox_events.payload` includes it

### Structured logging
- `pino` with JSON output
- Required fields: `request_id`, `user_id`, `service`, `endpoint`, `method`, `status`, `latency_ms`, `transaction_id` (when applicable), `error.code` (on errors)
- HTTP access log middleware logs every request
- Disable body logging in prod (PII risk); allow in dev with `--log-level=debug`

### Error envelope
Already designed in phase 03. Now consolidate:
- `GlobalExceptionFilter` in `src/common/`
- Catches all thrown exceptions (HttpException, custom, unhandled)
- Maps to `{ error: { code, message }, request_id }`
- Stack traces NEVER in response; only in logs

### Metrics (Prometheus)
Expose `GET /metrics`:
- `http_requests_total{method,route,status}` counter
- `http_request_duration_seconds{method,route}` histogram with [0.005, 0.01, 0.05, 0.1, 0.5, 1, 5]
- `payments_total{type,status}` counter
- `db_query_duration_seconds{query_name}` histogram
- `outbox_pending` gauge (current unpublished count)
- `processed_events_total{consumer,status}` counter
- `redis_errors_total` counter
- Process metrics via `prom-client` defaults

### Health endpoints
- `/health` — liveness, 200 always if process is alive
- `/ready` — readiness, checks:
  - DB reachable (`SELECT 1`)
  - Redis reachable (PING)
- 200 if all up; 503 with `{ db: 'ok', redis: 'down' }` if any fail
- Use `@nestjs/terminus`

### Alerting (documented, not implemented)
- `docs/RUNBOOK.md` (optional): "if `payments_failed_total{reason='INTERNAL'}` rate > 5/min for 5 min, page on-call"

## Structure & Tools

### Folder: `src/observability/`
- `logger.module.ts` (pino)
- `request-id.middleware.ts`
- `metrics.controller.ts` exposing `/metrics`
- `metrics.service.ts` for custom metric registration
- `metrics.interceptor.ts` for HTTP timing

### Folder: `src/common/` (extend)
- `global-exception.filter.ts`
- `error-codes.ts`
- `base.exception.ts`

### Tools
- `nestjs-pino` for request-scoped logger
- `prom-client` for metrics
- `@willsoto/nestjs-prometheus` for integration
- `@nestjs/terminus` for health checks

### Where
- App root (`main.ts` / `app.module.ts`): request-id generation, access logging, global filter, metrics endpoint, health endpoints
- All modules: throw with `BaseException(code, message, httpStatus)` — never raw `throw new Error(...)`

## Acceptance Criteria

- [ ] Every API response has `X-Request-Id` header
- [ ] Every log line includes `request_id`, `service`
- [ ] All errors return the same envelope; no stack traces exposed
- [ ] `GET /metrics` returns Prometheus format with HTTP + payments + outbox metrics
- [ ] `/ready` returns 200 when all deps up
- [ ] `/ready` returns 503 with details when Redis down
- [ ] `/health` always 200 if process is alive
- [ ] Logs are valid JSON, one object per line
- [ ] Custom metric `payments_total` increments on every payment

## Self-test

> A user reports "I tried to send money at 2pm and got a weird error". You have no logs from the user except their user_id and the approximate timestamp. Within 60 seconds, how do you find the relevant request?

Path:
1. Check `payments_failed_total{reason="INSUFFICIENT_BALANCE"}` metric — spikes correlate with user reports
2. Grep logs for `user_id` + time window
3. Find `request_id`
4. Grep all logs for `request_id` (single process = single log file)
5. See the full chain: HTTP request → JWT validation → FOR UPDATE → CHECK fired → 422 returned

Monolith wins here: ONE log file, ONE process. No correlation across services needed.
